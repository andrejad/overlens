# Building, installing and running

- **REQ_DEPLOY_001** — A multi-stage Dockerfile (Node build, then Go build, then a minimal "distroless" image) produces one container that serves both the API and the web app. There is no nginx, and `VITE_API_URL` is left unset at build time, so the app talks to its own server (REQ_FE_087).
- **REQ_DEPLOY_002** — `docker-compose.yml` uses absolute host paths from `${DATA_DIR}` and `${CONFIG_DIR}` (with a comment at the top explaining why), mounts the backup folder as a volume, and has a `/health` check and `restart: unless-stopped`.
- **REQ_DEPLOY_003** — `make build-linux` builds the Linux program, and a systemd service file is provided with the exact install commands.
- **REQ_DEPLOY_004** — `make build-windows` builds `roadmap.exe` from Linux, with the exact NSSM commands (the program is not a native Windows service, so `sc.exe create` alone fails with error 1053; `sc.exe` is used only to start, stop and query), including the service account and working folder.
- **REQ_DEPLOY_005** — `start.sh`/`stop.sh` run the server (127.0.0.1:8080) and Vite (port 5173, proxying `/api`) with the PID file `.dev-servers.pid`. Development happens on Linux (WSL Ubuntu), so there are no PowerShell dev scripts; the built app itself runs on Linux, macOS and Windows. Stop kills the child processes, removes the files, and reports stale or missing ones.
- **REQ_DEPLOY_006** — `docs/DEPLOY.md` covers the Linux, Windows and Docker (Portainer) routes, in that order, and how to restore a backup by hand.
- **REQ_DEPLOY_007** — `README.md` gets a new developer running locally in under five minutes.
- **REQ_DEPLOY_008** — Every code change is recorded with date and time in the maintainers' development log, which is not part of this repository. `CHANGELOG.md` is the changelog for users: Keep a Changelog, one section per release, and a plain line under `[Unreleased]` for each change users will notice. *(Changed 2026-10-22, decision: the development log was `CHANGELOG.md`.)*
- **REQ_DEPLOY_009** — `GET /health` answers `200 {"status":"ok","version":"<version>"}` (the version of REQ_DEPLOY_010; *changed 2026-10-21: it now carries the version*) without logging in and without touching the session table, and `503` with the plain-text body `database unreachable` when the database can't be read (REQ_API_019 is unchanged). The container has no shell, so the binary offers `-healthcheck`: it asks its own `/health` on the configured port and exits 0 on `200`, 1 otherwise. The compose and container health checks run it.
- **REQ_DEPLOY_010** — The binary takes `-version` and logs its version, build time and commit when it starts. Every build made through the Makefile (`make run`, `make build`, `make build-linux`, `make build-windows`) and the Docker image stamp them in *(changed 2026-10-21: `make run`, `make build` and the image were unstamped)*. The version is the git tag `vX.Y.Z` the build is made from, without the `v` (built from a later commit it reads like `1.0.0-3-gabc1234`, with uncommitted changes `-dirty` is added); where there is no such tag, or no git at all (the Docker and CapRover builds), it is the content of the `VERSION` file in the repository root. `make version` prints it.
- **REQ_DEPLOY_011** — The Docker image runs as a non-root user, has `/data` and `/backups` volumes, and is configured by `ROADMAP_*` environment variables (REQ_CFG), so no config file is needed inside the container. The bootstrap admin password can come from `ROADMAP_BOOTSTRAP_ADMIN_PASSWORD_FILE` or the environment. The container starts with no config file when the `ROADMAP_*` variables are set (a missing config file is then not an error). The compose file publishes the port on the company VPN interface address only, taken from an environment variable.
- **REQ_DEPLOY_012** — `docs/DEPLOY.md` also covers first start and the one-time bootstrap admin, restoring a backup by hand (stop, replace `roadmap-database.db`, remove `-wal` and `-shm`, start), upgrading (back up, replace binary or image; schema upgrades run on start and are logged), and the cookie and proxy trade-offs of the VPN deployment.
- **REQ_DEPLOY_013** — The app can be deployed with CapRover from the same image (a `captain-definition` file), with its own persistent `/data` volume. `docs/DEPLOY.md` has a CapRover section: app settings, the persistent directory, environment variables, HTTPS and the health check path. The app does not trust `X-Forwarded-For`, so behind CapRover's proxy all visitors share one address for the login lockout (REQ_AUTH_011/017); five failed logins by anyone lock all logins for 15 minutes. The docs state this as an accepted risk. Because CapRover ends HTTPS at its proxy, the app sees plain HTTP and would send the session cookie without `Secure`; the config key `cookie_secure` (`auto` by default; `true` always sets `Secure`) is set to `true` there. *(Amended 2026-10-19, decision: a general CapRover route, no longer described as a public demo.)*
- **REQ_DEPLOY_014** — `docs/DEPLOY.md` has a Kubernetes chapter, after the CapRover one, that runs the same image: a complete manifest with one replica and the `Recreate` strategy (the data is one SQLite file), a Secret for the admin password, volumes for `/data` and `/backups`, `/health` probes and user 65532, plus notes on VPN-only exposure, TLS at the ingress, backups, restoring and upgrading.
- **REQ_DEPLOY_015** — *(2026-10-21, decision)* Versions follow Semantic Versioning: the major number goes up when something users depend on breaks (an API contract, a config setting, or a database that an older version wrote and the new one can no longer open), the minor number for new features, the patch number for fixes only. A release sets `VERSION` to `X.Y.Z` and is committed and tagged `vX.Y.Z`; `CHANGELOG.md` gets its `[Unreleased]` section renamed to `[X.Y.Z] — date` and is the only changelog that is published. After a release `VERSION` becomes the next planned version with `-dev` (e.g. `1.1.0-dev`).
- **REQ_DEPLOY_016** — *(2026-10-22, decision)* Each release offers ready downloads that need nothing else installed: Windows x64 (`.zip`), Linux x64 and ARM64, macOS Apple Silicon and Intel (`.tar.gz`), named `overlens-<version>-<platform>-<arch>`, plus a `SHA256SUMS` file. Each holds the program (`roadmap` / `roadmap.exe`, REQ_OVR_014), `START-HERE.txt` (how to start it on each system, including the warnings an unsigned program gets), a ready `roadmap.conf`, `LICENSE` and `CHANGELOG.md` (no `roadmap.conf.example`, and no `README.md`: the repository's front page shows it; *changed 2026-10-24, decision*). The ready `roadmap.conf` (kept as `deploy/roadmap.conf`) has every setting filled in and explained: admin `admin` with the password `admin` (to be changed after the first login), port 8080, sample data on, the AI connection on, daily backups at 04:00 kept 10 days, audit entries kept 365 days, logins valid 365 days, log level INFO, production, cookie `auto`, and everything the program writes in one folder beside it: `overlens-data/db/roadmap-database.db`, `overlens-data/logs`, `overlens-data/backups`. So the program starts with a double-click. `make release-files` builds them all into `dist/release/`; the release uploads them to its GitHub release.
- **REQ_DEPLOY_017** — *(2026-10-22, decision)* When the program has started (the port is open and the backup scheduler has logged its next run), the last thing it shows in its window, after an empty line, is a framed message: "Overlens is running.", "Open in your browser:" with `http://localhost:<port>`, and "Keep this window open. Press Ctrl+C to stop Overlens." When this start created the first admin it also says to log in as that user with the password from `roadmap.conf` and to change it; it never shows the password. The message goes to the window only, not to the log file. Lines logged later (each request) follow it.
